# 红果短剧 Android · 原生重写（开发分支）

## 当前 `rewrite-web-native`：开心果数据源与视频核心

默认匿名剧集目录、搜索、排行、筛选、剧集分集、播放模型及渐进式 MP4
已迁移至开心果 Android 的 `openhongguo` SDK `0.2.1-kx.1`。
播放器仍是本项目唯一的 `BackgroundPlaybackService` / Media3 ExoPlayer；
实际视频字节由开心果的 `CencDataSource` 实时按需解密并提供给播放器，
不再在匿名播放路径获取旧 `RemoteVideo`。预加载沿用同一 SDK
请求下一集模型与 CENC 索引；磁盘缓存改为新的指纹隔离缓存。

刷剧页面新增推荐来源状态提示（同时显示在首次加载页与播放页）：
账号请求中、成功获取账号官方推荐、暂无新增、请求失败和匿名推荐都会明确标注。
此提示按实际请求身份及返回的新作品更新；“账号官方推荐已获取”不代表
客户端能确认服务端已经进行个性化排序。点击提示可查看解释。

**保留**目前 rewrite 的 UI、导航、刷短剧手势、后台媒体通知、PiP、
应用内小窗、账号、评论和社交功能。用户主动开启的账号推荐仍走
原有账号会话，因为开心果 SDK 仅支持匿名目录，不能替代该登录能力。
明确配置的独立 HTTP API 后端也继续受支持。旧原生核心仍保留用于
账号与社交兼容模块。

上游的匿名请求可能因设备注册、风控或内容权限失败；
并非所有 HLS/DASH 或需要登录的内容都可经开心果的 MP4 解密器播放。
迁移细节见 [docs/KAIXINGUO_MIGRATION.md](docs/KAIXINGUO_MIGRATION.md)。


这是 **全新 Android 工程**，不是旧版 `com.hongguo.android` 的 UI 修补。

## 设计基准

- 网页版导航结构：推荐 / 榜单 / 最新 / 筛选，顶部搜索、历史、收藏、分享与下载任务。
- 顶部明确可见「设置」入口：独立设置页包含内容来源、API 地址、详细日志预览、日志开关、清空和 TXT 导出。
- 统一 Insets：Activity 显式 edge-to-edge，ApplicationRoot 一次性处理 safeDrawing + IME；首页、设置页 Scaffold 禁止重复处理系统栏 Insets；播放器底部控制区可滚动，适配手势导航、三键导航和刘海屏。
- 诊断事件存储在本机私有目录（256 KB 上限），记录阶段、耗时、HTTP 状态和错误代码，不收集 URL、搜索内容和凭据；经 Android 文档选择器导出。
- 主要 App 页面使用 Kotlin + Jetpack Compose，官网验证 Activity 的外层采用原生 Android View；视频使用 AndroidX Media3。
- 不引入旧 Android 项目的 Activity、播放器、设备注册、缓存、状态或 Hook。
- 单向数据流：DramaViewModel -> AppState -> Compose；本机数据、剧场分页、下载任务、播放地址重试及视频 Surface 已逐步拆入独立模块，模块边界详见 docs/ARCHITECTURE.md。
- 统一的剧集、分集、分页和错误模型；收藏/历史保存在本机并限定为 200 条。
- 历史只在 Media3 实际渲染首帧后记录，避免播放失败留下误记录。
- 独立包名 `com.yagay.hongguo`，能与旧版并排安装进行验收。

## 当前工程状态（重要）

**这是重写工程的第一阶段，不是已完成的独立客户端。**

当前集成独立的原生内容和播放核心 `com.hongguotv.core`，来源为
`tsukiyo-zero/hongguoTV`（GPL-3.0-only），并使用独立适配器 `NativeHongguoSource`
与 Media3 `NativeVideoDataSource` 接入。默认无需 Node 服务：推荐、真人/漫剧/AI 榜单、
分类、题材筛选、搜索、分集读取和匿名视频播放均走原生链路。

官网目录数据源 `NativeWebsiteSource` 保留作公开内容参考；
**上游是否返回有效视频模型受其当前服务状态和风控影响，本工程不保证一定可播放。**

可选连接开源 `sunnysky123/hongguo-web` 的 **HTTP API 合约**，以使用视频播放、
分类筛选、更多榜单与下载任务；手机需要使用可达的服务器地址。
接口包括：`/api-key`, `/rank`, `/latest`, `/browse`, `/filters`,
`/search`, `/episodes`, `/stream`, `/img`, `/share/resolve`, `/download/task`。
初始不配置服务器时优先使用原生推荐、搜索及视频接口；推荐接口不可用时回退官网公开目录。失败时显示脱敏错误代码。

**仍未完成或需要验收**：
- 真机验证匿名设备注册、签名 GET/POST 取址、解密及首帧；上游可能返回空响应。设备注册 DNS/超时、播放模型空响应和不支持的解码格式均有独立诊断代码；
- 已接入本机单集 MP4 导出，使用 Android 文件选择器选择保存位置，下载中可查看进度和取消；
  进程退出后不支持断点续传，跨设备账号同步与批量下载仍待完善；
- 真机实测及无障碍/旋转/网络切换的完整回归。

播放请求失败可能源于上游设备注册/风控，不是简单更换播放器或重做界面就能保证解决。

## 登录账号与刷短剧推荐（2026-11-08）

- 登录账号成功后**不会自动将账号 Cookie 用于推荐接口**。设置 → 账号与隐私 →「刷短剧使用登录账号」默认关闭，需用户自行开启；账号页面右上角也能切换同一开关。
- 开启后，刷短剧「综合」与「真人」的官方推荐请求（包括真人分类补充推荐）都使用经验证的登录会话；会话只发送到相关官方推荐接口，**不发送用户观看行为或伪造点赞数据**。
- 开关切换、账号完成验证或退出时，推荐队列会更新请求身份并重新取数；若正在播放，保留当前视频，重建后续推荐，不释放 Media3 播放器。
- 本地日志仅记录 `REELS/ACCOUNT_REQUEST_MODE` 或 `ANONYMOUS_REQUEST_MODE` 等状态码，不记录 Cookie、账号标识或视频标题。账号 Cookie 随请求发送**不等于服务端保证个性化**：推荐内容是否与官方 App 的个人首页完全一致，需要同一登录身份下的实际对照验证。

## 跨 App 系统画中画（PiP，2026-11-08）

- 正在播放时，**返回桌面或切换到其他 App**：在 Android 12+ 上会按系统自动进入画中画；Android 8–11 用 Activity `onUserLeaveHint` 进入。播放器右上角及 App 内底部迷你播放器都有手动「画中画」入口。
- 画中画使用系统允许的**竖屏 9:16** 比例以缩小窗口宽度；支持系统的拖动、双指缩放、双击切换最小/最大尺寸、拖向边缘暂时收起等操作（具体取决于 Android/OxygenOS 版本）。**像素级最小尺寸受系统限制**，不承诺任意缩小或突破系统 PiP 最小值。
- 小窗仅显示来自唯一 `MediaSessionService` / `ExoPlayer` 的画面；**不创建新播放器、悬浮窗权限、Root/LSPosed Hook**，也不重新获取播放地址。PiP 内的系统媒体控制继续由 Media3 MediaSession 管理。
- 展开 PiP 时恢复之前的全屏或 App 内迷你播放器页面。主动关闭系统 PiP 窗口则关闭播放会话；背景音频策略与 App 内小窗分开。
- 主 Activity 清单声明 `supportsPictureInPicture` 和屏幕配置变化；仅 Android 12+ 使用 `setAutoEnterEnabled` / `setSeamlessResizeEnabled`，Android 8–11 通过显式进入兼容。自动进入只允许**正在播放且当前媒体 ID 对应已选视频**的状态，暂停、加载和切集中不自动触发。
- 需要真机确认系统是否允许 PiP、横竖屏切换、拖拽缩放、首次进入/退出的画面绑定、关闭窗口释放服务，以及 Android 26–36 的版本兼容；源码提交本身不代表已完成 Debug CI 或设备测试。

## App 内迷你播放器（2026-11-08）

- 播放时点击左上角返回或 Android 返回键，**不关闭视频**：返回首页/我的列表，在底部导航栏上方显示带视频画面的小播放器；进入搜索、设置、账号、剧集详情等页面，小播放器固定在对应页面底部。
- 小播放器直接绑定当前唯一的 `MediaSessionService` / `ExoPlayer`，**不创建第二播放器**，保留当前画面、进度、连续播放和系统媒体卡。它在各页面使用**同一个底部视频容器**，不再随底部导航和页面切换销毁视频 Surface；下一集/下一部加载期间保留上一帧或封面，避免短暂黑屏或小窗消失。点击小播放器恢复全屏；可在小窗播放/暂停；只有点击关闭按钮才真正释放正在播放的媒体资源。
- 点击播放器剧名进入详情时仍在下方播放，不再为了打开详情而暂停/销毁视频；从详情返回可回到全屏。自动播下一集时保持小窗，详情页主动选集则打开全屏；重复点当前集只接回原播放器。
- 这是**App 内迷你播放器**，不是跨应用显示的 Android 画中画（PiP）或系统悬浮窗。它不会申请悬浮窗权限，也不会在其他 App 上叠加窗口。
- 静态源码检查不代替实际 Debug 构建或真机验证。需测试前后台切换、详情页选集、连续切集及 Media3 视频画面重新绑定。

## 后台播放与媒体通知（2026-11-08）

- 使用 AndroidX Media3 1.8.0 的 `MediaSessionService`，由前台媒体服务持有**唯一 ExoPlayer**；Compose 页面只挂接 PlayerView 视频画面，进入后台或锁屏不会因为页面 `ON_STOP` 而暂停。
- **仅使用系统 Media3 媒体控制卡**，显示剧名、当前集数/总集数、真实视频时长、当前播放时间和可拖动进度条，提供播放/暂停以及前一项/后一项。已移除重复的普通通知栏进度卡与每秒 `NotificationManager.notify()` 调用；系统媒体界面的呈现与进度刷新由 Android/OxygenOS 决定。
- 普通播放：上一项/下一项等同于**上一集/下一集**；刷短剧：对应**上滑/下滑切上一部/下一部**，并保留队尾加载及隐藏作品过滤规则。
- `MediaSessionService` 通过 `addSession(session)` 注册媒体会话，由 Media3 管理**必需的前台服务通知**、媒体控制与音频焦点。支持后台进度存档、定时暂停、自动跳片尾和网络唤醒；在 App 内进入详情及其他页面时通过下方迷你播放器继续播放。仅为剧集更新提醒保留 `POST_NOTIFICATIONS` 权限与相关设置。
- 依据 AndroidX 官方后台播放范例和 `hongguoTV` 原生媒体流，配套 `BackgroundNavigationPolicyTest`。**本分支尚未完成真实设备端验证**：尤其要测熄屏、耳机、来电、系统杀进程、Android 14+ 前台服务以及通知切集后的片源恢复。

## 抖音式交互与公开评论（2026-11-07）
- 全屏 `VerticalPager`：**上滑下一集 / 下滑上一集**，仅当前页有 Media3 播放器；切换时取消旧剧集请求。
- 单击画面暂停/继续，双击收藏（带爱心反馈），长按临时 2× 倍速、松开恢复；媒体会话允许退到后台、锁屏后继续播放。
- 切换分集时沿用独立核心的短期下一集播放模型预取；一次请求最多带一集预测，避免连续滑动产生无限后台请求。
- 右侧固定操作栏：收藏、分集评论、弹幕开关、Android 系统分享、单集下载、选集。
- 评论底部抽屉：匿名只读分集评论，支持分页；上游不可用时尝试官网有限公开评论，并明确标记。
- 弹幕：时间点读取、播放时间同步、横向移动；默认关闭，可在播放器快捷开关和播放器内「播放设置」面板启用。禁止虚构弹幕。
- 交互分离：视频纵向翻页、评论抽屉竖向滚动、进度条拖动互不共用手势识别器。
- 目前**不支持评论发布、服务器点赞或账户授权**；相关功能不能用虚假的本地行为代替。真实评论/弹幕可用性需手机端验证。

## Danmaku and video obstruction fix

- The native video player now owns a **separate video viewport** above the full-drama dock.
  The bottom CTA and orange seek control are outside the video; neither can cover
  burned-in subtitles.
- Default aspect mode is \`FIT\` to preserve the entire image. The top-right
  overflow menu can optionally switch to full-bleed \`ZOOM\` and back.
- Timed comments use measured text width to travel completely from the right
  edge to the left edge; deterministic four-lane assignment avoids text
  collisions and preserves lane positions through pause/seek.
- Movement is driven by Media3 position, not wall-clock time. Seeking and
  pausing update/stop the overlay.
- Diagnostics distinguish \`DANMAKU READ_EMPTY\` from \`READ_NONEMPTY\` so a
  successful request with no visible comments can be diagnosed separately.
- Independent unit tests cover lane contention, non-overlap, seek progress,
  width-aware animation boundaries, and stable ordering.


## 自动加载右侧评论数

- 进入分集后立刻独立请求首批评论及服务端 `total`，无需先点击右侧评论图标；不阻塞视频取址和首帧。
- 右侧评论按钮显示公开服务端评论总数（包含 0）；正在加载时显示省略号，失败时保留「评论」文字，不假装 0。
- 点击评论只展示正在加载或已缓存的结果，不取消重发；仍保留手动刷新和分页。
- 切集或退出时取消过时评论请求并清空旧数字，确保不会混用其他分集的统计。
- 收藏和喜欢的公开计数现从整剧官网与原生分集统计读取；分享总数没有可靠来源，仍不展示虚构统计。


## 自动公开互动统计（真人短剧播放器）

现在打开剧集后会并行读取两路只读数据，完全独立于 Media3
播放地址、评论列表和弹幕请求：

1. 红果官网播放器页面 \`seriesSocialInfo\`：
   \`series_favorite_count\` 为全剧收藏数，
   \`series_like_count\` 为全剧点赞数。
   该格式可参考 zfdang/hongguo-open-player 的
   \`src/server/native/hongguo.js\`（仅参考协议字段；未复制其 AGPL 代码）。
2. 红果匿名原生 \`POST /novel/player/video_detail/v1/\`：
   \`followed_cnt\` 为全剧追剧/关注数，
   \`digg_cnt\` 为全剧点赞数，
   \`series_play_cnt\` 为全剧播放量；
   各集 \`video_list[].comment_count\` / \`digged_count\` 分别为分集评论数和点赞数。
   接口与字段参考 Apache-2.0 的
   [beilunyang/openhongguo](https://github.com/beilunyang/openhongguo)。

所有数字必须校验短剧 ID 和分集视频 ID。**缺失或异常字段显示为未知，
不写成 0；客户端点击收藏或本地喜欢不修改公开数字。** 收藏和追剧不是同一
指标：如果只能拿到 \`followed_cnt\`，界面会额外标记「追剧」；
爱心优先显示分集点赞数，只有全剧点赞数时会额外标记「全剧」。
分享总数尚无可核实的数据字段，不显示虚构数值。

两路读取有独立失败日志 \`SOCIAL WEB_FAIL\` / \`SOCIAL APP_FAIL\`；
成功时为 \`SOCIAL WEB_READY\` / \`SOCIAL APP_READY\`。缓存最近打开剧集
的结果约两分钟，但每次进入仍会刷新；切集不重复请求全剧数据，
直接按当前分集 ID 取对应指标。实际数据能否返回取决于上游服务，
不能以 Debug CI 通过代替真机网络验证。


## 功能扩展 · 2026-11-07

本次变更只触及 \`rewrite-web-native\` 开发分支，继续维持单一原生
Kotlin/Compose/Media3 工程及 Debug-only CI。

### 内容发现与连续浏览
- **搜索联想**：直接复用已存在的
  \`ContentRepository.searchSuggestions()\`，输入 2 字后延迟约 300ms
  查询并取消过期请求；搜索历史只保存本机，最多 12 条，可清空。

## 连续播放预加载强化（2026-11-09）

- Media3 仍由 `BackgroundPlaybackService` 独占。播放器在原生视频源准备完毕后，提前安排下一集的播放模型与首段字节；首帧到达后不会再人为等待 850ms。
- 相同目标的预加载任务不会因为首帧回调重复提交而被取消。预加载仅在剧集 ID、画质、预算及内容代际仍一致时发布，避免快速滑动后把旧视频交给当前播放器。
- N+1 继续按用户选定的 1/2/4/8/16 MiB 预算预热；新增独立的 N+2 低优先级 2 MiB 预热槽位。进入 N+1 时，若 N+2 已准备，直接提升为下一集缓存；若尚在加载则等待已有任务，不重复取流。
- 完结集的视频模型准备后，在延迟 1.2 秒的低干扰窗口中启动下一部官方推荐预取。即便首帧回调迟到，也不需要等到播放结束才开始查询下一部；真正跨剧衔接仍取决于官方推荐、取址与真实设备网络。
- 关闭预加载、切换画质或预算、退出播放及跨剧导航时会释放不再适用的 N+2 资源；通过 `PREFETCH_CACHE_HIT/MISS`、`CACHE_PREFIX_KIB_*`、`SWITCH_TO_FIRST_FRAME`、`LATER_VIDEO_PREPARED/WARMED`、`FINALE_EARLY_WARMUP` 等本地诊断事件区分预加载命中与临时取流。
- 这是一套边界严格的内存预热，不会整集离线下载；HTTP 后端仍按原有播放逻辑工作，原生预加载针对 native source。现有 Debug CI 会在推送时运行，实际无缝切换仍需真机验证。

## 近期播放缓存延长（2026-11-09）

- 系统 Media3 服务把已经退出当前播放的原生 `RemoteVideo` 放入有界 LRU 缓存，按 `vid + quality` 精确命中。由单一服务持有对象，复用时转移所有权，不创建第二个 ExoPlayer。
- 近期流由原来单项、90 秒改为最多六项、最多 15 分钟（计时从放入缓存开始），并限制前缀缓存字节合计约 48 MiB；达到任何一个上限都优先淘汰最旧缓存。
- 用户明确关闭播放器或服务销毁时立即关闭并清理全部缓存，不在进程外持久保存，也不将解密视频写入公共存储。进程死亡或系统回收内存后缓存不会保留。
- `RECENT_STREAM_STORED`、`RECENT_STREAM_REUSED`、`RECENT_STREAM_MISS`、`RECENT_STREAM_EVICTED`、`RECENT_STREAM_EXPIRED` 日志可确认是复用还是重新取流。实际命中与峰值内存仍需 Debug 真机测试。

## Native 视频磁盘缓存与智能预加载（2026-11-09）

- **统一数据通路**：应用内唯一的 Media3 播放服务在原生 `NativeVideoDataSource` 外侧接入 `CacheDataSource`；缓存对象为已经由 `RemoteVideo` 处理、播放器实际消费的字节，不缓存原始加密 HTTP Range 地址，也不改变原生请求或解密协议。自定义 HTTP API 模式暂不进入该原生缓存层。
- **单一缓存实例**：应用启动时在 IO 线程初始化 `SimpleCache`，目录为应用专属 `cacheDir/native_stream_cache_v1`，采用 2 GiB LRU 最大容量，按缓存片段最近使用时间清理超过 7 天的条目（每小时至多扫描一次）。系统可能提前清理 `cacheDir`，因此不是持久离线下载。
- **避免串流混用**：缓存键按视频 ID、目标画质、媒体长度及准备后实际读取的前 1024 字节内容指纹派生。无法取得完整指纹时**禁用本次磁盘缓存**，仍允许直接流式播放；防止服务端替换同 ID/长度媒体后误用旧片段。缓存键本身不包含原始视频 ID、URL、Cookie。
- **预热共享**：正常播放把真实播放数据自动写入磁盘；N+1、N+2 和下一部推荐预热时，完成 `RemoteVideo.warm` 后通过同一个 Media3 CacheDataSource 把实际媒体范围写入磁盘。切回已播放视频、重启 App 后仍需先取得合法的播放模型与流指纹，之后可复用已缓存的字节，不保证断网完整播放。
- **网络策略**：默认仅非计费、已验证的 Wi-Fi 下执行后台额外预取；移动网络默认不预取后续视频，但正常播放仍允许联网并写缓存。设置可独立切换 Wi-Fi 积极预取和移动网络额外预取。播放源/网络变化、预取禁用时会取消不再有效的预热任务。
- **用户控制**：设置 → 视频缓存与预加载，可关闭磁盘缓存、查看当前约略占用、切换预加载网络策略、确认后手动清除视频缓存。清除时要求停止当前播放器，避免删除正在使用的缓存片段；不会删除收藏、历史或专门导出的离线文件。
- **诊断**：`DISK_CACHE INDEX_READY`、`SOURCE_CACHE_READY/FALLBACK`、`READ_HIT_KIB_*`、`USER_CLEARED` 与现有的 `PREFETCH_CACHE_HIT/MISS` 区分真实磁盘命中和内存热流复用。新增测试涵盖不同画质/内容的 key 隔离、7 天过期和同长度流内容变化。
- **数据与隐私**：缓存存放在 Android 应用私有目录，不会加入本机备份或用户文件目录；数据是播放器使用的**已解码容器字节，默认不额外进行静态加密**。不用于绕过 DRM、访问授权或制作永久离线副本；若上游禁止相关缓存或流受 DRM 保护，则需禁用该缓存路径。
- **验收**：现阶段源码提交不等于真机通过，必须在 Debug CI 成功后按冷启动、复播、切画质、网络切换、缓存满额、低存储、后台 PiP、强制结束 App 以及上游模型更新等场景复测。

## 刷剧模式双候选预加载（2026-11-10）

- 当前正在播放的视频仍由唯一的 Media3 播放服务读取；当前剧下一集（N+1）是最高优先级，继续使用用户选定的 1/2/4/8/16 MiB 预算，N+2 使用 2 MiB。
- 刷剧模式另设独立的**官方推荐双候选窗口**。当当前视频源准备成功、首次画面出现或官方推荐新批次到达时，会重新预测向上滑动的下一部、再下一部，跳过隐藏、重复及当前作品。此流程不依赖 N+1 全部预热结束。
- 下一部短剧提前获取详情与第一集视频模型，并采用**不超过 8 MiB** 的上限（同时服从用户预加载预算）。起播首段优先发布，之后增长缓存并写入已有 Media3 私有磁盘缓存。若正在播放的视频尚未起播，短暂让出启动带宽；若 N+1 尚未就绪，只进行有限等待，不再直接放弃下一部。
- 再下一部短剧提前获取剧集详情；等下一部已准备起播片段后，低优先级准备第一集的**2 MiB** 小缓存，同时保留一个待交接的 `RemoteVideo`，无需创建第二个播放器。当用户连滑进入下一部，再下一部可提升为新的最近候选缓存。

## 预加载失效诊断与修复（2026-11-10）

根据用户 2026-11-10 07:21 UTC 导出的诊断日志：`PREFETCH_CACHE_MISS` 34 次、`PREFETCH_CACHE_HIT` 3 次，`MODEL_FAIL_PLAYBACK_EMPTY_RESPONSE` 11 次，另有模型网络 I/O/超时错误；`DISK_CACHE READ_HIT_KIB_*` 证实曾命中磁盘片段，不能据此推断跨剧预加载已完成。

- **预取门控**：修正某些 Android/OEM 将 Wi-Fi 标记为计费网络或尚未通过系统连通性验证，导致整套提前加载被直接跳过的问题。Wi-Fi 开关允许时可预取；其他网络仍遵循移动网络开关。播放本身不受预取开关影响。
- **上游错误**：下一集及下一部短剧播放模型遇到空响应或瞬时 `IOException` 时，仅有限重试一次；下一部/再下一部详情请求网络失败也允许一次短延迟重试，不进入无限请求循环。
- **滑动交接**：用户上滑时不再立即启动下一目标的预热任务并取消仍在进行的旧目标任务。对正在预取的目标允许短暂等待并转移 `RemoteVideo` 所有权，避免本次预加载尚未准备完就开始第二次相同的模型请求。命中日志 `INFLIGHT_DRAMA_REUSED`；超时回退 `INFLIGHT_DRAMA_TIMEOUT`。
- **诊断可见性**：`PREFETCH_GATE_DISABLED`、`PREFETCH_GATE_NETWORK_*`、`SWIPE_PREFETCH_SKIP_*`、`SWIPE_PREFETCH_WAIT_RECOMMENDATIONS`、`NEXT_PRELOAD_FAIL_*` 可直接区分用户设置、网络策略、推荐队列缺失、上游异常。
- **测试**：增加纯网络策略测试，确保 Wi-Fi 模式与移动网络额外预加载开关相互独立。现有刷剧两候选测试仍应通过。
- **确认 APK**：旧日志没有 `SWIPE_PREFETCH_PLAN_READY` 等双候选事件，不能证明已安装最新分支的 Debug APK。请使用本次提交后的 Debug 构建复测，重点观察 `SWIPE_PREFETCH_PLAN_READY`、`NEXT_DRAMA_PREFETCH_SCHEDULED`、`SECOND_VIDEO_PREPARED`、`INFLIGHT_DRAMA_REUSED`、`DISK_CACHE READ_HIT_KIB_*`。

- 当前视频缓冲起播优先：如果还没确认首帧，N+1 最多让出约 2.4 秒启动带宽，一旦首帧确认立即开始；跨剧后台请求则不再仅因为 `SOURCE_READY` 便抢占起播阶段，而由 `FIRST_FRAME` / 后台播放确认事件再计划。

## 2026-11-10：非缓存视频冷启动优化（多开源项目对比）

对比了 `beilunyang/openhongguo` 的匿名设备/可重试网络错误模型、`N3urda/hongguoTV` 的 Kotlin Range 加载与播放器复用，以及 `aston314/hongguo-tv` 的健康来源优先与分阶段播放诊断。参考其原则但不搬运其他项目的身份轮换或播放器架构，沿用本仓库的注册、签名、CENC 与 Media3 服务。

**具体代码问题与修复**：

- `NativeHongguoSource.openVideo(preload=true)` 此前未将 `preload` 传入 `ContentRepository.streamLadder(speculative)`；导致非关键 N+1/N+2/跨剧预取可能消耗和前台同样的多路恢复预算。已改用最多**一条健康线路、4 秒**的后台轻量模型预算；成功后仍准备真实媒体字节，失败时前台照常解析。
- `NativePlaybackResolver` 以前允许一次空模型重试再叠加最多两次网络重试，而核心每轮已包含最多四条线路与 8 秒期限；现在统一限制为**最多一次外层恢复**，短暂退避（空模型 700 ms、临时网络 800 ms），防止重复完整模型轮次无限拖慢首帧。重试仅针对当前 VID/画质有效。
- `ContentRepository.streamLadder` 以前第二条候选线路一律新建空连接池，重试结束再回收；即便只是上一条返回空模型也会损失健康 HTTP 连接复用。现在仅**实际连接/超时/DNS**等传输错误才使用隔离的新连接池，非传输类回退延用 OkHttp 共享池。
- `RemoteVideo.prepare` 的 MP4 索引请求以前使用与长时间视频播放相同的 **45 秒单次请求超时**。现在允许为**起播索引请求单独使用**基于共享连接池的派生客户端：连接 4 秒、读取 8 秒、前台总 12 秒（预取 8 秒）；索引解析成功后，Media3/Range 读取继续使用既有可靠的流媒体客户端，不把短启动期限套到整集播放。
- `PLAYBACK RANGE_PREPARED` / `RANGE_FAIL` 现在包含毫秒耗时，并另记脱敏的 `CDN_CANDIDATE_N_READY/FAILED`；结合 `MODEL_READY`、`SERVICE_WAIT` 和 `SWITCH_TO_FIRST_FRAME` 能判断接口、CDN 头部与 Media3 哪一段占主要时间。
- 增加 `PlaybackRoutesTest` 以检查单条后台线路、成功路径优先和空路径冷却。所有普通 push 仍只构建 Debug；本次分支不执行签名 Release。

**限制**：这会缩短不必要的网络回退与 CDN 死等，却不能保证官方播放模型、运营商链路、不同 CDN 节点一定稳定或每次起播达到固定秒数。尤其首次冷加载仍需要设备注册、视频模型与 MP4 索引。真机需核对新日志中 `MODEL_READY ms`、`RANGE_PREPARED ms` 和首帧时间，以确认实际收益。
